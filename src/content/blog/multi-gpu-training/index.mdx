*An intuition-first walk from the single-GPU training loop to a 16,000-GPU production run. For software engineers who haven't trained a model before. About a 50-minute read.*

### 1. The single-GPU loop

Training a neural network on one GPU is a four-line loop.

```python
pred = model(x)            # forward
loss = criterion(pred, y)  # one scalar
loss.backward()            # backward
optim.step()               # update weights
```

Repeat the four lines a few hundred thousand times and you have a trained model. The whole post is about adding GPUs to this picture without breaking the loop. Spoiler: you can't quite do that. Each rank has to negotiate with its peers between steps, and most of what follows is about making the negotiation cheap, or hiding it behind compute.

There is nothing to do here yet, but burn the four boxes into your visual memory. Every later figure will either split one of these boxes across more GPUs or repeat all of them on more GPUs.

The forward pass walks the model. Every linear layer is a matrix multiplication, every nonlinearity is an element-wise function. The output is a prediction. The loss is a single scalar, the difference between the prediction and the truth, on this one batch.

The backward pass walks the model in reverse, applying the chain rule. The output is the gradient of the loss with respect to every parameter. PyTorch lazily computes this; calling `.backward()` walks the autograd graph and fills `.grad` on each parameter tensor.

The optimizer step uses the gradient to move the parameters slightly in the direction that decreases the loss. With Adam, the dominant optimizer in practice, the move involves three running statistics per parameter: the parameter itself (an FP32 master copy), the first moment of the gradient (an exponential moving average, called *m*), and the second moment (the EMA of squared gradients, called *v*).

So far, plain. Here's the part that becomes load-bearing later.

In the common mixed-precision Adam budget, each parameter is effectively stored twice. There's an FP32 master copy that the optimizer reads and writes, and a half-precision copy (BF16 or FP16) that the forward and backward passes use. The half-precision copy makes training fast on tensor cores; the FP32 master keeps the optimizer's tiny updates from being swallowed by half-precision rounding error. Per parameter, this setup needs:

- 2 bytes for the half-precision weight, used in forward/backward
- 2 bytes for the half-precision gradient, filled by backward
- 4 bytes for the FP32 master copy, owned by the optimizer
- 4 bytes for `m`
- 4 bytes for `v`

Total: 16 bytes per parameter.

Memorise that number. A 70B-parameter model trains in 70 × 10⁹ × 16 = 1.12 *terabytes* of state. An H100 has 80 GB. We are already in trouble, and we haven't even talked about the *activations* the forward pass leaves behind for backward to consume.

That's why we need more than one GPU. The model doesn't fit. Sometimes the model fits but the data is too slow; we'll get to that. The first force is memory.

### 2. Two GPUs, one negotiation

Add one GPU, and the loop has to learn to share.

The setup is the same on each rank: a full copy of the model, a full copy of the optimizer state, the same code. The only thing different is what data each rank sees. Each rank gets a different slice of the batch. With two GPUs and a batch of 32, GPU 0 processes samples 0-15 and GPU 1 processes samples 16-31. Both run forward, both compute their local loss, both run backward.

At the end of backward, the two gradients disagree.

This is where the negotiation begins. The gradient of the loss on the full batch of 32 is the average of the gradient on samples 0-15 and the gradient on samples 16-31. So if both ranks average their gradients before the optimizer step, every rank takes exactly the same step a single GPU on the union batch would have taken. The training loss follows the same trajectory as the single-GPU run, and the only difference is wall-clock: each rank only had to do half the forward and backward, so the step took half the time.

Averaging gradients across N ranks is a *collective* called *all-reduce*. We're going to spend a lot of time on it.

<Figure caption="One DDP step. Each rank runs forward and backward in parallel, then all-reduces gradients, then steps the optimizer. The all-reduce bar widens with rank count; the right-hand readout is its share of one step. Compute parallelises; comm becomes the tax." figNum={2}>
<DdpStep client:visible />
</Figure>

Drag the slider to add GPUs. Scrub through one step. The compute phase (forward + backward) stays roughly constant: more GPUs means each one does less work in parallel. But the all-reduce phase grows. By N=16, on this model, the all-reduce takes about as long as the compute. We've added GPUs and hit the point where adding more would do nothing.

This is the central tension of the rest of the post. Compute parallelises beautifully across GPUs. Communication does not. Every technique from here on is about pushing the all-reduce phase down or hiding it.

Three optimisations make DDP usable at scale. All of them are about the all-reduce.

The first is *bucketing*. Calling all-reduce once per parameter tensor would be a disaster: a transformer has thousands of parameter tensors, most of them small, and NCCL all-reduce throughput is dominated by per-call overhead at small sizes. PyTorch's DDP coalesces gradients into ~25 MB buckets and all-reduces one bucket at a time. Each call lands on the bandwidth-bound part of the throughput curve.

The second is *comm-compute overlap*. The backward pass produces gradients in the reverse order of forward: the last layer's gradients land first, the first layer's gradients land last. As soon as bucket K's gradients are all ready, DDP fires its all-reduce on a separate NCCL stream. The rest of backward keeps computing the gradients for buckets K-1, K-2, and so on. The last bucket's all-reduce finishes a hair after backward does. Mental model: the all-reduce isn't really a separate phase, it's painted on top of backward.

The third is *gradient accumulation*. If you want a larger effective batch but each GPU's memory only fits 8 samples at a time, you accumulate gradients over several forward-backward passes before stepping the optimizer. PyTorch wraps this in a context manager:

```python
with model.no_sync():
    for x, y in micro_batches[:-1]:
        loss = criterion(model(x), y)
        loss.backward()        # accumulates locally, no all-reduce
loss = criterion(model(micro_batches[-1]), y)
loss.backward()                # all-reduce fires here
optim.step()
```

K accumulation steps coalesce into one collective instead of K.

That's most of what data parallel is. The code for the full loop looks like this:

```python
model = DDP(model)
for x, y in batches_for_this_rank:
    pred = model(x)
    loss = criterion(pred, y)
    loss.backward()
    optim.step()
```

Compared to single-GPU, only one line is new: the `DDP(model)` wrap. The loop body is unchanged. The negotiation happens inside `loss.backward()`.

We've sketched the cost of all-reduce as a single number ("it takes time"). We haven't said how N machines actually reach consensus on a vector without one of them becoming a bottleneck. That's the next section.

### 3. The ring all-reduce

How do N machines average a vector without one of them becoming a bottleneck?

The naive answer is to nominate a leader. Every rank sends its gradient to GPU 0, GPU 0 sums and divides, GPU 0 sends the result back to everyone. Two phases of communication, each of size M (the full gradient vector). It works, but GPU 0's network link saturates first, and at scale it becomes the bottleneck. It also wastes the bandwidth of every other GPU's outbound link.

A better way uses a ring.

<Figure caption="Ring all-reduce. Each rank's vector is split into N chunks; cells fill as contributions accumulate. The first N-1 scrubber steps are reduce-scatter (cells grow, one chunk per rank lights up green when fully summed); the next N-1 are all-gather (the green cells copy around the ring until every rank holds every fully-summed chunk)." figNum={3}>
<RingAllReduce client:visible />
</Figure>

Drag the slider for N. Scrub from step 0 through step 2(N-1). The first N-1 steps are the *reduce-scatter*; the next N-1 steps are the *all-gather*.

Set N=4 and watch step 0. Each rank holds the full gradient vector divided into 4 chunks; call them a, b, c, d. At step 0, every rank sends one chunk to its right-hand neighbor and receives one chunk from its left. Each rank accumulates the arriving chunk into its own value at the same position. After step 0, four sums exist around the ring, one per chunk position.

At step 1, the chunks rotate again. Each rank forwards a different chunk (the one that just arrived) and accumulates again. After N-1 = 3 steps, exactly one slot on each rank holds the sum of its values across all N ranks. The chunks have lapped the ring once, and the partial sums have grown along the way.

That's the reduce-scatter phase. Each rank ends up owning one chunk of the fully reduced result, the others still partial.

Now do another lap, but this time without adding. Each rank passes its fully-reduced chunk forward; the neighbor copies it into the matching slot. After N-1 more steps, every rank holds every fully-reduced chunk. That's the all-gather phase.

Total: 2(N-1) steps, each step shipping M/N bytes. Per-rank traffic:

> 2(N-1)/N × M

which approaches 2M as N grows and stops growing. This is the *bandwidth-flat* property: doubling the GPU count does not double the time to all-reduce a fixed vector. Tree algorithms have O(log N) latency but pay O(M log N) bandwidth and saturate the root link first. Ring trades a log factor in latency for a flat bandwidth cost. Once the gradient is megabytes, ring wins.

Patarasuk and Yuan proved in 2009 that 2(N-1)/N × M is the lower bound for any all-reduce algorithm. The ring saturates it. In real NCCL runs the library auto-selects among ring, tree, CollNet/NVLS/PAT-style variants, and topology-aware hybrids. Ring is the clean bandwidth-optimal model to keep in your head; production collectives are the topology-tuned version of the same pressure.

There's one move worth holding onto. The ring split the work into two halves: reduce-scatter (each rank ends up with one chunk's full sum) and all-gather (every rank ends up with every chunk). For DDP we ran both back-to-back to recover the full all-reduce. Each half is a useful primitive on its own, and we'll see them reused in the next section to do something the all-reduce alone cannot.

### 4. When the model doesn't fit

Data parallel solved a wall-clock problem. It did not solve a memory problem.

Picture training a 70B-parameter model with mixed-precision Adam. From section 1, that's 16 bytes per parameter, so the parameters, gradients, and optimizer states together come to 70 × 10⁹ × 16 = 1.12 terabytes. An H100 has 80 GB of HBM. A 70B Adam run is 14× over budget on memory before we've allocated a single activation tensor.

Sliding ranks to 32 leaves the bar untouched: every replica holds the full 16Ψ. Switching to GB300 (288 GB) lifts the line but still doesn't reach a 70B model. The cluster-total readout is the bill." figNum={4}>

Now drag the GPU-count slider up. Notice the bar doesn't shrink. With DDP, every rank holds the full state, so adding GPUs scales compute, not memory. That is the wall we hit.

Three things take memory in a training step. *Parameters* are 2 bytes per param in BF16; *gradients* are 2 bytes per param; the *optimizer state* is 12 bytes per param for Adam, broken into 4 for the FP32 master copy, 4 for `m`, and 4 for `v`. The optimizer state is the elephant. It's 12 of the 16 bytes per parameter, and the optimizer is the only thing that touches it. Forward never reads it. Backward never writes it.

This was the insight that gave us ZeRO. With N GPUs, you don't need every rank to hold every byte at every moment. You can partition the state across ranks and reconstruct what you need when you need it, by talking.

The first thing to partition is the optimizer state, because it's the biggest and the cheapest to spread out. We're going to do that next. And we're going to do it without adding any communication on top of what DDP already paid.

### 5. ZeRO and FSDP

ZeRO-1 partitions the optimizer state across N ranks. Each rank holds 12/N bytes of optimizer state per parameter instead of 12.

Here's the move that makes this work without paying extra communication. Recall from the last section that DDP's gradient all-reduce was actually a reduce-scatter followed by an all-gather. After reduce-scatter, every rank already holds the fully-reduced gradient for one chunk of parameters. After all-gather, every rank holds every chunk.

ZeRO-1 reuses the first half. After reduce-scatter, rank `i` holds the fully-reduced gradient for chunk `i`. Rank `i` is also the only rank that needs to update its optimizer state for chunk `i`, because rank `i` is the only rank that holds it. So rank `i` runs the optimizer step locally, on its slice. There's nothing else to do for chunk `i`: rank `i` has the fully-updated parameter slice.

Then we all-gather the updated parameters. Every rank ends up with every chunk's fresh parameters, ready for the next forward pass.

Total comm: reduce-scatter on gradients + all-gather on parameters. Same 2(N-1)/N × M as a regular all-reduce. ZeRO-1 saves 12 - 12/N ≈ 12 bytes per parameter of memory and pays *zero* extra communication.

ZeRO-2 also partitions the gradients. The same dataflow handles it: each rank only holds the gradient slice it needs to update its optimizer state slice. Each step still costs reduce-scatter + all-gather. ZeRO-2 saves another ~2 bytes per param, again at zero extra comm.

ZeRO-3 partitions the parameters themselves.

This is the one that costs extra. Forward and backward both need every parameter, but each rank now only holds 1/N. The fix: just-in-time all-gather. Before forward of layer K runs, every rank all-gathers the parameters for layer K, runs the layer, and immediately frees the gathered copy. Same on backward. We trade 16Ψ → 16Ψ/N bytes per param of memory for `2 × num_layers` extra all-gathers per step. Communication goes from 2Ψ (DDP) to 3Ψ (ZeRO-3): 50% more.

The catch is latency. Each layer's all-gather is small (a single layer's parameters), and the latency-bound part of the NCCL throughput curve dominates. Across `2 × num_layers` calls per step, the latency adds up.

The trick that makes this affordable is *prefetching*.

<Figure caption="FSDP forward pass with all-gather prefetch. The top row is the naive serialised schedule for reference. The bottom two rows split the work across a comm stream and a compute stream: with prefetch on, the all-gather for layer K+1 fires while forward of layer K is still running, so the gather never lands on the critical path. Scrub through one forward pass. The all-gather for layer K+1's parameters fires while layer K's matmul is still running. The two run on separate streams. By the time forward reaches layer K+1, its parameters are already in memory. The gather doesn't show up on the critical path. Backward does the same trick in reverse.

This pattern, ZeRO-3 with prefetching, is what PyTorch's FSDP implements. The Hugging Face Ultra-Scale Playbook is direct: "PyTorch's native implementation of this stage is called FSDP. We'll just refer to it as ZeRO-3 in this book." For the rest of the post, ZeRO-3 and FSDP mean the same thing.

A real production data point: Llama 3 405B was trained with FSDP as the data-parallel axis, with one further refinement. From the paper: "We use fully sharded data parallelism (FSDP), which shards the model, optimizer, and gradients … For model shards we do not reshard after forward computation to avoid an extra all-gather communication during backward passes." On their 16K-H100 cluster, the trade between the memory of keeping the gathered parameters around and the saved all-gather on backward came out in favor of keeping them. That choice is exposed today as `reshard_after_forward=False` on PyTorch's `fully_shard` API.

Which brings us to FSDP2.

### 6. FSDP2 and the DTensor abstraction

FSDP1 has been deprecated in favour of FSDP2. The new entry-point API is `fully_shard`, and the change isn't cosmetic.

FSDP1 represented sharded parameters as one giant flat tensor per layer, with custom logic to wrap and unwrap them. That worked but it didn't compose well: combining FSDP1 with tensor parallel required custom code at every seam.

FSDP2 represents each sharded parameter as a *DTensor*. A `DTensor` is a regular `torch.Tensor` with one extra piece of metadata: a *placement* on a *device mesh*.

A `DeviceMesh` is just an n-dimensional array of GPU ranks. A 1D mesh for plain DDP on 8 GPUs is `[0, 1, 2, 3, 4, 5, 6, 7]`. A 2D mesh that combines data parallel (size 4) and tensor parallel (size 2) on the same 8 GPUs is `[[0,1], [2,3], [4,5], [6,7]]`. The mesh names the topology of the cluster.

Each DTensor declares a placement on each axis of the mesh. Three placements cover everything we need:

- `Shard(dim)`: the tensor is split along `dim` across that axis; each rank holds `1/(axis size)` of the tensor.
- `Replicate()`: the tensor is fully copied to every rank along that axis.
- `Partial(reduce_op)`: each rank holds a *partial* value, and a reduction (usually sum) is pending.

On a 2D `[dp, tp]` mesh, a parameter can be sharded one way along the data-parallel axis (FSDP-style) and a different way along the tensor-parallel axis (the column-parallel matmul we'll see next section). Same tensor, two simultaneous shardings, no custom code at the seam. Each operator on the DTensor knows enough about the placements to insert the right collective.

This is the substrate that makes 4D and 5D parallelism composable. Llama 3 describes a 4D mesh ordered `[TP, CP, PP, DP]`. DeepSeek-V3 uses a 3D mesh `[EP, PP, DP]` and skips tensor parallelism entirely. The user doesn't have to write code for the cross product.

Two practical knobs from `MixedPrecisionPolicy` are worth naming. `param_dtype` controls what dtype parameters are computed in (typically BF16). `reduce_dtype` controls what dtype the gradient reduce-scatter happens in (sometimes FP32, instead of BF16, to avoid loss-of-precision in gradient sums on very large clusters). They're separable, and the separation matters for stability.

That's all the FSDP2 we need for this post. The takeaway is the abstraction. A parameter is a `DTensor`. A `DTensor` knows how it's sharded across the mesh. Every later section is just a different choice of placements.

### 7. Splitting one matmul

There's a different way models become un-fittable. Sometimes the model fits but a single matrix multiplication inside it doesn't. A 70B-param model has a hidden size around 8192; the FFN expansion gives intermediate matmuls of `[batch × seq, 8192] @ [8192, 32768]`. At long context that's tens of GB of activation per layer. One matmul doesn't fit on one GPU.

Tensor parallel (TP) cuts the matmul itself across GPUs.

The trick is algebraic. Think of an MLP block as `Z = GeLU(X·A) · B`, where A is the up-projection (8192 → 32768) and B is the down-projection (32768 → 8192).

Split A column-wise: `A = [A₁, A₂]` (each rank gets half the output columns). Each rank computes its half of `X·A` locally with no comm. GeLU is element-wise, so each rank applies it locally too. We're left with `[Y₁, Y₂]` distributed across two ranks.

Now split B row-wise: `B = [B₁; B₂]` (each rank gets half the input rows, paired with its `Y` half). The product `Y · B = Y₁·B₁ + Y₂·B₂`, and each rank computes its term locally. The two terms still need to be summed across ranks. That sum is one all-reduce.

<Figure caption="Two-rank tensor-parallel matmul. X is replicated; A is column-sharded so each rank computes a partial Y. In column-only mode the halves are incoherent for the next layer. Toggling on the row-sharded B closes the loop: each rank now produces a partial Z, the all-reduce at the bottom sums them, and every rank ends with the full Z." figNum={7}>
  <TpMatmul client:visible />
</Figure>

Toggle to "column-only." Notice that each rank ends up with a partial `Y` and the next layer can't make sense of it on its own; the input to the next matmul would be different on each rank. Toggle to "column + row." The all-reduce closes the loop: every rank ends up with the full `Z`, and the next layer can run as if nothing was split.

PyTorch's autograd needs help to thread through these splits. Megatron-LM introduced two symbolic operators that wrap the comm. `f` is identity in forward, all-reduce in backward. `g` is all-reduce in forward, identity in backward.

The `f` operator sits at the entry of a TP block. Forward, the input is already replicated across ranks, so `f` does nothing. Backward, the input gradient needs to be summed across ranks before propagating upstream. The `g` operator sits at the exit. Forward, the partial outputs need to be summed. Backward, the upstream gradient is already replicated, so `g` does nothing. Together they make the autograd graph through a TP block look exactly like a single-GPU autograd graph from the optimizer's perspective.

Self-attention is the same trick on a different axis. With `h` heads and a TP group of size `t`, each rank gets `h/t` heads. The Q, K, V projections are column-parallel along the head dimension; each rank computes its head's attention locally with no cross-rank comm; the output projection is row-parallel and closes with a `g` all-reduce. Total: two all-reduces per transformer layer in forward, two in backward.

Two all-reduces per layer is a lot. For a 32-layer model that's 64 all-reduces per forward-backward step, each one needing all `t` ranks to synchronise. TP is bandwidth-hungry, and the bandwidth has to be very fast. The practical constraint is sharp: TP works inside one NVLink-connected node (where bandwidth is 600+ GB/s), and falls apart across InfiniBand (50 GB/s). TP=8 is the typical maximum on H100, matching the 8 GPUs in one node.

That's why TP stays small. To go bigger, we need to attack a different axis. We also need to fix a memory problem TP just created.

### 8. The activation tax: sequence parallel

Tensor parallel cut the matmul. It didn't cut the activations between matmuls.

Inside a transformer block, the parts that aren't matmuls (LayerNorm, dropout, residual additions) are element-wise. They don't benefit from being split, and TP didn't split them. Every TP rank holds the full `[batch × seq, hidden]` activation tensor at every LayerNorm and dropout. With long context (say 32k tokens) and a 70B model, that's hundreds of MB per element-wise region per layer. The activation memory dwarfs the parameter memory.

Sequence parallel (SP) fixes this.

The idea is local. The element-wise regions don't need the full activation; they operate independently along the sequence axis. So shard those regions along sequence instead. Every rank holds a `1/t` slice of the activation in those regions. On entry to the matmul region, all-gather the activation along sequence. On exit, reduce-scatter the result back. The original Megatron `g` all-reduce splits cleanly into reduce-scatter + all-gather of the same total bytes, by the Patarasuk-Yuan equality.

The bar is stacked into matmul activations (sharded by TP), element-wise regions (full under TP-only, sharded under TP+SP), and the attention-score subblock (which scales as s²). Drag the sequence slider: at 1k–4k SP shrinks the bar dramatically; at 32k attention takes over and SP has nothing left to fix." figNum={9}>
  <TpSp client:visible />
</Figure>

Compare TP-only vs TP+SP. Drag the sequence-length slider out to 32k. Watch the activation memory of the LayerNorm and dropout regions shrink to `1/t` of its TP-only size. Total comm volume is unchanged. Peak activation memory drops a lot.

There's still residual activation pressure that TP+SP doesn't catch. Attention's softmax-attention-dropout subblock holds an `[batch, heads/t, seq, seq]` tensor that scales as O(s²) in sequence length. For very long context that becomes the dominant memory cost.

Korthikanti et al's "selective activation recomputation" paper (2022) handles this. They checkpoint exactly the attention subblock during forward and recompute it during backward. The cost is one extra forward pass through the attention region, about 2.7% extra FLOPs. The saving: the attention activation drops out of the memory budget entirely. That paper reports roughly 70% memory savings on the activation side for GPT-3 175B with TP+SP.

The combined recipe of the last two sections is what most production training stacks ship today: tensor parallel inside an NVLink-connected node, sequence parallel splitting the non-matmul regions, and selective recomputation of attention.

We've reached the size where this stops scaling. With TP=8, the matmul fits. With TP+SP, the activations fit. But the model can be deep enough that even with this, a single layer's parameters and gradients don't all fit on a node. Going TP=16 across two nodes throws the bandwidth budget away.

When the layers themselves are too many for one node, we split *across* layers. That's pipeline parallel.

### 9. Pipeline parallel and the bubble

Pipeline parallel (PP) gives each GPU a contiguous slab of the model's layers. With K GPUs and L layers, GPU 0 owns layers 1..L/K, GPU 1 owns L/K+1..2L/K, and so on. Forward propagates left to right through the pipeline; backward propagates right to left.

The naive version is bad. Send a batch through layer 0; while it's being processed, every other GPU is idle. When it finishes layer 0, send it to layer 1; now layer 0's GPU is idle. Only one GPU is ever busy. We've turned K GPUs into one GPU plus K-1 spectators.

The fix is *micro-batching*. Split the batch of size N into M micro-batches of size N/M. Send micro-batch 1 through layer 0. As soon as layer 0 finishes with micro-batch 1, hand it off to layer 1, and start micro-batch 2 on layer 0 in the same time slot. By the time micro-batch 4 is on layer 0, micro-batch 3 is on layer 1, micro-batch 2 is on layer 2, and micro-batch 1 is on layer 3. The pipeline is full.

But it took K-1 steps to fill the pipeline (the *warm-up*), and it'll take K-1 steps to drain it after the last micro-batch leaves layer 0. Those steps are partially idle. We call those gaps the *bubble*.

<Figure caption="K stages on the y-axis, time on the x-axis. Toggle between GPipe (full forwards then full backwards, with the bubble showing as the empty triangles top-left and bottom-right), 1F1B (the steady region in the middle alternates F and B per stage, capping activation memory at K micro-batches), and Interleaved 1F1B (each stage owns v=2 chunks of layers so the warm-up triangle is half as wide). Drag K to widen the pipeline, M to feed it more micro-batches; the bubble percentage on the right is what the prose's formula gives you." figNum={10}>
  <PipelineSchedule client:visible />
</Figure>

Drag K and M. The bubble fraction is roughly `(K-1)/(M + K-1)`. With K=4, M=4, the bubble is 3/7 ≈ 43%, awful. Pump M to 16 and it drops to 3/19 ≈ 16%. With M=64 it's under 5%. Pipeline parallel needs many micro-batches to be efficient.

Toggle the schedule between GPipe, 1F1B, and Interleaved 1F1B.

GPipe (Huang 2018) is the simplest. Run all M forwards through the pipeline first, then all M backwards. Bubble fraction `(K-1)/(M + K-1)`. Cost: every micro-batch's forward activations live until backward consumes them, so peak activation memory per stage is `O(M)`.

1F1B (Narayanan 2021) keeps the same first-order bubble but improves activation memory dramatically. After the warm-up, each stage alternates one forward and one backward. The backward of micro-batch `i` consumes its forward activations and frees them, immediately. Activations only accumulate for ~K micro-batches per stage instead of M. Same speed, less memory. 1F1B is what Megatron-LM and most production stacks ship.

Interleaved 1F1B is the next refinement. Instead of giving stage `d` a contiguous block of layers, split the model into `K · v` chunks and assign chunks `d, d + K, d + 2K, …` to stage `d`. Each micro-batch crosses each stage `v` times instead of once, so the warm-up triangle is `v×` shorter:

> bubble fraction ≈ (1/v) · (K-1)/M

Cost: `v×` more communication volume because each micro-batch's activations cross each stage boundary `v` times. On a fast NVLink topology this trade is typically worth it.

There's a subtle thing about pipeline parallel that's worth naming. The optimizer step only happens once per *batch* (after all M micro-batches have completed forward and backward), not once per micro-batch. The gradient on each parameter is the sum across the M micro-batches. If you also have data parallel wrapping the pipeline, the DP gradient all-reduce happens once per batch on top of that.

We're not done with the bubble. There's a 2024 schedule that cuts the bubble nearly to zero by feeding the pipeline from both ends simultaneously.

### 10. DualPipe: a near-zero bubble

DeepSeek-V3 shipped a pipeline schedule in late 2024 called DualPipe. It nearly eliminates the bubble, in two moves.

The first is *bidirectional micro-batching*. Instead of feeding micro-batches from one end, feed them from both. Micro-batches 1..M/2 enter from the left at layer 0; micro-batches M/2+1..M enter from the right at the last layer. They flow toward each other. Each stage holds two streams of micro-batches: one traveling left-to-right (forward of the left-half batches), another traveling right-to-left (forward of the right-half batches, which from a single stage's perspective looks the same shape).

The two streams overlap exactly where naive pipelines have bubbles. The warm-up triangle on stage `d` is filled by the parallel work of the right-half stream's traversal. The drain triangle is similarly filled.

The second move is *backward splitting*. Each backward pass for a chunk is split into two phases. *Backward-for-input* (B) produces the gradient passed upstream. *Backward-for-weights* (W) produces the gradient stored locally for the optimizer. The earlier ZeroBubble paper showed these can be scheduled separately: B is on the critical path, W is not. DualPipe schedules W into the gaps that the bidirectional flow doesn't already fill.

Cells are colored by stream so the right-going batches are visible filling the slots that 1F1B leaves idle. Drag the scrubber to walk through one step on both schedules at once." figNum={11}>

Scrub through one DualPipe step. The bubble has gone from a `(K-1)·(F+B)`-shaped triangle to roughly `(K/2 - 1)·(F&B + B - 3W)`. For K=16 with similar F, B, W times, that's about half the bubble of 1F1B at the same K and M. Peak activation memory grows by `(K+1)/K`, roughly 6% on K=16.

DualPipe overlaps two more communications. Forward and backward chunks fuse all-to-all comm (for MoE, see the next section) and PP comm into the same kernel slot, with what DeepSeek calls "warp specialization" and ten communication channels. From their paper: "both all-to-all and PP communication can be fully hidden during execution."

DeepSeek-V3's actual production parallelism layout deserves a callout, because it shows how the choices compound at the frontier. They run 16-way pipeline parallel, 64-way expert parallel, and ZeRO-1 data parallel. There is *no tensor parallel*. They argue that DualPipe makes the pipeline's bubble small enough that they can use a deeper pipeline instead of TP, and the model is sparse enough (MoE) that EP replaces what TP would have done. The whole training run finishes in 2.788M H800 GPU-hours.

That's the production data point that says all the techniques in the post can compose. The missing axis is expert parallel, which is what makes DeepSeek-V3 a sparse model in the first place.

### 11. MoE and expert parallel

Mixture-of-experts (MoE) is a different kind of scaling. Instead of making every parameter participate in every token's forward pass, you make most parameters *sit out* of most tokens. The model has `E` parallel "expert" sub-networks; for each token, a small router picks `k` experts (Switch uses top-1, Mixtral top-2, DeepSeek-V3 uses eight routed experts plus one shared expert) and only those experts process that token. The total parameter count grows by `E×`, but the FLOPs per token stay much closer to the active expert count.

DeepSeek-V3 has 671B total parameters but only 37B active per token. Mixtral 8x7B has 56B total, ~13B active. The model is large; the compute is small.

This creates a new comm pattern. Token `i` lives on rank `r`. Its assigned expert lives on rank `r'`, possibly far away. Every layer needs to *send* tokens to their expert's home, run the expert FFN, and *send* the outputs back. The collective that does this is *all-to-all*.

<Figure caption="Capped top-1 routing for one token, shown as a simple teaching model. Drag x picks the selected expert; drag y picks the token's home rank. When the expert lives elsewhere, blue and green arcs show dispatch and return all-to-all traffic. Cell fill shows expert load against capacity; overflow marks imbalance. DeepSeek-V3 uses top-8 plus a shared expert and does not use this dropped-token Switch-style cap." figNum={12}>
  <MoeRouting client:visible />
</Figure>

Pick a different expert with the drag. In this simplified top-1 version, the router picks one expert. When that expert lives on a different GPU, the token is shipped via all-to-all to the GPU that holds that expert. The expert's FFN runs. A second all-to-all returns the result back to the token's home rank. Top-k systems do the same pattern with more selected experts per token: two all-to-alls per MoE layer in forward, two more in backward.

All-to-all is harder to schedule than all-reduce. Each rank sends a different chunk to each other rank, instead of all chunks being summed. The total bytes are driven by the number of dispatched token activations, but the latency, link pressure, and kernel efficiency depend heavily on EP group size and whether tokens are spread evenly across experts. Hot experts overload their host GPU; cold experts idle. *Load balance is the central problem.*

Switch Transformer (Fedus 2021) introduced the canonical balancing trick: an *auxiliary loss*.

> loss_aux = α · N · Σᵢ fᵢ · Pᵢ

where `fᵢ` is the fraction of tokens dispatched to expert `i` and `Pᵢ` is the mean router probability mass on expert `i` over a batch. This loss is minimised when both `fᵢ` and `Pᵢ` equal `1/N`, which means uniform routing. The aux loss is added to the main training loss, and the router learns to balance itself.

The catch: the aux loss distorts the gradient. The router is being pulled by two forces, one toward "the right expert for this token" and one toward "uniform routing." The compromise hurts model quality.

DeepSeek-V3 introduced an *auxiliary-loss-free* balancing trick. Instead of an extra loss term, they add a per-expert *bias* `bᵢ` to the routing scores before the top-k selection. After each step, they compare each expert's actual load to the target load: if expert `i` is over-loaded, they decrease `bᵢ` by a tiny amount γ; if under-loaded, they increase it. The bias isn't part of the gradient. It only affects which experts get picked, not how the gradient flows through them.

The right sparkline plots load std-dev across the run, with the dot marking the current step. The trick: aux-loss-free's bias updates pull experts toward uniform without sending a balancing gradient through the router." figNum={13}>

</Figure>

Toggle aux-loss vs aux-loss-free, scrub through training steps. The aux-loss curves stabilise around uniform load but with visible oscillation. The aux-loss-free curves converge faster and tighter, and the gradient through the router is left alone.

DeepSeek-V3 also adds a *sequence-wise* balance loss as a safety net. The aux-loss-free trick handles balance over a full batch; the sequence-wise loss prevents one bad sequence from sending all its tokens to two experts.

The all-to-all geometry on DeepSeek-V3's cluster is worth one specific number. They train on 2048 H800s, 8 GPUs per node connected by NVLink (160 GB/s) and across nodes by InfiniBand (50 GB/s). The all-to-all kernels saturate IB+NVLink using only 20 SMs out of an H800's 132. That's about 15% of the chip's SM budget burning *just on data movement*. The rest is compute. That is the tax.

That's four axes of parallelism (data, tensor, pipeline, expert). There's one more, and it matters when contexts get very long.

### 12. The million-token problem: context parallel

When context length goes to 32k, 128k, 1M, even sequence parallel inside a TP group isn't enough. The attention matrix `QKᵀ` is `s × s`. At s=1M that's `10¹²` entries before head dim is multiplied in. No single GPU holds that.

Context parallel (CP) shards along the sequence axis at the *attention* level. A CP group of size `c` splits the sequence into `c` chunks; each rank holds `s/c` tokens worth of Q, K, V activations. The attention computation needs every Q to see every K and V eventually. That seeming impossibility is fixed by ring attention.

<Figure caption="Eight GPUs arranged in a ring. Each rank holds a fixed Q block and a rotating KV block. At each step every rank computes partial attention against the KV block it currently holds, then forwards that block to its right-hand neighbor. After eight steps every Q has seen every K and V. The right panel shows the per-rank token count and the local KV cache size; the bottom-left legend keys the colors." figNum={14}>
  <RingAttention client:visible />
</Figure>

Drag the slider for sequence length out to 1M. Scrub through one rotation of the ring. Each rank starts holding its own KV block. At each step, every rank computes partial attention on its current Q against the KV block it currently holds, then forwards the KV block to its right-hand neighbor. After `c` steps, every Q has seen every K and V.

The blockwise softmax stays exact through the ring. Online softmax accumulation lets you compute `softmax(qkᵀ)v` over chunks of K and V incrementally, by keeping a running maximum and a running sum and updating them with each new chunk. The math is the same as flash-attention's online accumulation. Ring attention is the distributed cousin.

There are two flavours. *Pass-KV* rotates the K and V blocks while Q stays fixed. That's the natural choice for *prefill*, when all tokens of a sequence are processed at once. *Pass-Q* rotates Q while K and V stay fixed. That's the natural choice for *decode*, when tokens stream in one at a time and the KV cache is large. The Context Parallelism for Scalable Million-Token Inference paper (2024) reports 1M-token prefill on Llama 3 405B in 77 seconds using pass-KV across 128 H100s.

For training, CP usually rides alongside the other axes. Llama 3 declares its parameters on a 4D mesh with order `[TP, CP, PP, DP]`. The order matters. From inner-most to outer-most, the parallelism dimensions are arranged so that the highest-bandwidth comm (TP all-reduces) lives on the fastest links (NVLink within a node), and the lowest-bandwidth comm (DP gradient all-reduces) can use the slower links (InfiniBand across nodes). The rule of thumb: put bandwidth-hungry parallelism first.

That's all five axes. The post can now ask "what's actually in production" and answer with a composition of the things we just built.

### 13. FP8 in production

Half precision saved memory; FP8 saves compute throughput. An H100's tensor cores have roughly 2× the FP8 tensor throughput of BF16. If your GEMMs are the bottleneck and you can train in FP8 without losing accuracy, that is a huge wall-clock lever. Communication, pipeline bubbles, and non-GEMM kernels keep the end-to-end speedup below the raw tensor-core ratio.

The catch is that FP8 E4M3 has only three explicit mantissa bits. Activations and weights routinely contain large outliers, and a per-tensor scale tuned for the typical value will saturate or zero those outliers. Naive FP8 doesn't converge.

DeepSeek-V3 made FP8 work for a 671B-parameter model. The recipe matters because it's one of the clearest public production FP8 training recipes.

Three rules.

The first is *fine-grained scaling*. Activations are scaled per-token per-128-channels (a `1×128` tile). Weights are scaled per-`128×128` block. Outliers stay localised to their tile. A spiky channel in one row doesn't blow up the scale for the whole tensor. From DeepSeek's paper: "this approach ensures that the quantization process can better accommodate outliers by adapting the scale according to smaller groups of elements."

The second is *what stays out of FP8*. The three GEMMs in the linear layer (forward Fprop, backward-input Dgrad, backward-weight Wgrad) all run in FP8. Everything else stays in BF16 or FP32: the embedding, the output head, the MoE gating module, the norms, and the attention softmax. These components are the ones most sensitive to precision loss, and their compute cost is small enough that FP8 wouldn't save much there anyway.

The third is *high-precision accumulation*. Hopper's FP8 tensor cores accumulate FP8 × FP8 into an internal format that retains around 14 bits of precision, which DeepSeek measured as not enough for stable training. Their fix: every 128 K-axis steps inside a GEMM, the partial sums are promoted out of the tensor-core accumulator and re-accumulated in FP32. The kernel pays careful scheduling work to recover numerical precision without giving up the FP8 throughput win.

The result: in DeepSeek's baseline MoE validation, the FP8 relative loss error vs BF16 "remains consistently below 0.25%." For the full 14.8T-token DeepSeek-V3 run, the stronger public claim is operational: they report no irrecoverable loss spikes and no rollbacks.

DeepSeek's hardware wishlist (V3 §3.5) is colour worth ending on. They explicitly ask NVIDIA for higher FP8 accumulation precision in tensor cores, native support for tile- and block-wise quantization, and online quantization. The most aggressive FP8 production team is on record saying current Hopper tensor cores leak precision and current kernels burn SMs on data movement. The fact that they made it work anyway, on a 2048-GPU cluster, is the data point.

What's left is to compose the axes.

### 14. Composing the axes

We've collected five primitives. *Data parallel* with FSDP shards parameters, gradients, and optimizer state per-rank and all-gathers on demand. *Tensor parallel* cuts each matmul and threads autograd with `f` and `g` operators. *Pipeline parallel* splits layers and schedules with 1F1B or DualPipe. *Expert parallel* routes tokens to MoE experts via all-to-all. *Context parallel* shards the sequence axis and exchanges KV via ring attention.

A real training run uses several at once. Each axis lives on a dimension of a `DeviceMesh`. A parameter is a `DTensor` with a placement on each axis. Forward and backward each turn into a sequence of collectives, one per axis, scheduled with as much overlap as possible.

<Figure caption="64 GPUs as an 8x8 grid. Each cell is one GPU sliced into stripes, one per parallelism axis. Drag any cell; the cells that share a comm group with it light up that group's stripe. The selected GPU lights all five (or four) stripes because it's in every group with itself; every other lit cell shares exactly one axis. Toggle between the 5D layout (with EP, mocking DeepSeek-style) and the 4D layout (no EP, mocking Llama 3)." figNum={17}>
  <FiveDMesh client:visible />
</Figure>

Drag a GPU. The five colours light up the GPUs that share each of its parallelism groups. The TP and CP groups are tightly clustered (NVLink within a node), the PP and EP groups span nodes (InfiniBand), and the DP group typically spans many nodes. The mesh shape isn't chosen by ML. It's chosen by the network.

Two production examples.

Llama 3 405B uses a 4D mesh `[TP, CP, PP, DP]`. No expert parallel; it's a dense model. In the reported 8K-context configuration, TP=8, CP=1, PP=16, DP=128 on 16K H100s; for 128K context, CP rises to 16 and DP falls to 8. The DP axis is FSDP with `reshard_after_forward=False`. This run achieves 38–43% BF16 MFU. The axis order is chosen so the most bandwidth-hungry comm gets the fastest links: TP on NVLink, DP on InfiniBand.

DeepSeek-V3 671B-MoE (37B active) uses a 3D mesh `[EP=64, PP=16, DP]`. No tensor parallel. The MoE replaces what TP would have done; DualPipe makes the deeper pipeline cheap. The DP axis is ZeRO-1 only (optimizer state partitioned, params and grads still replicated), because the model is sparse and per-rank parameter memory is already manageable. On 2048 H800s, this run finishes 14.8T tokens in 2.788M GPU-hours. FP8 throughout the GEMMs.

The two configurations diverge because the models diverge. Llama 3 is dense and very deep; tensor parallelism is the right tool for the matmul. DeepSeek-V3 is sparse and wide (256 experts per MoE layer); expert parallelism is the right tool for the model.

Same primitives, different composition. That's the takeaway.

### 15. 2026 best practices

The decision is forced more by the hardware than by the model. The model picks ZeRO-3 vs PP vs EP at the coarsest level, but the exact configuration falls out of: how many GPUs you have, what's connected to what, the NVLink bandwidth within a node, the InfiniBand bandwidth between nodes, the model size, and whether the model is dense or sparse.

The recommended TP × CP × PP × EP × DP mesh updates underneath. The memory bar shows coarse optimizer/parameter state against the 80 GB cap; activations and framework overhead are omitted. Match the inputs to Llama 3 405B (dense, 16k GPUs, H100) or DeepSeek-V3 (MoE, 2k GPUs, H800) to land near the published configurations." figNum={18}>
  <DecisionCalculator client:visible />
</Figure>

Drag the model size up from 1B. At 1B parameters on a single 8-GPU node, plain DDP is correct: the model fits, the bandwidth is fast, no exotic axes are needed. Around the 7B/8B class, FSDP starts paying off. Per-rank optimizer footprint drops from roughly 112 GB replicated to roughly 14 GB when sharded across 8 GPUs. At 70B, you have to pick between (a) FSDP across many nodes with IB-bound all-gathers, or (b) TP=8 within a node + PP across nodes + DP at the top. Most production dense-model stacks choose (b) once single-axis FSDP is no longer the clean answer.

At 405B, you've reached Llama 3 territory: TP=8 + PP=16 + FSDP-on-DP, with CP added when long context requires it and `reshard_after_forward=False` on the FSDP axis. On 16K H100s, expect 38–43% MFU for the reported Llama 3 405B setup.

At 671B-MoE-37B-active, you've reached DeepSeek-V3 territory: EP=64 + PP=16 + ZeRO-1 + DualPipe, *no* TP, FP8 throughout the linear GEMMs, aux-loss-free balance with a sequence-wise safety net. The model is sparse, the comm pattern is all-to-all, and the trick is hiding both PP and all-to-all behind compute.

A few rules of thumb that fall out of the post:

- Pre-2024 you'd start with TP+PP. In 2026, if you're not at 100B+, start with FSDP and add axes only as memory or activation pressure forces them.
- TP almost always stops at 8 (one NVLink-connected node). Going higher trades NVLink for IB; the bandwidth cliff isn't worth it.
- PP wants M several times larger than K (the pipeline depth) for a decent bubble. At small global batch sizes you can't pay this; use FSDP instead.
- FP8 is production-proven on H100/H800 for carefully engineered sparse runs. Treat dense FP8 training as stack- and model-dependent, not automatic.
- Async TP (Megatron-Core) and Ladder-Residual are 2025 directions for hiding the TP all-reduce behind compute. Worth watching, not yet default.

Adding GPUs is easy. Getting them to agree is the entire field.
