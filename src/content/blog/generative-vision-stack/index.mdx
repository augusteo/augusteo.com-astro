*A sequel to [The Unified Vision Stack](/blog/unified-vision-stack) and [The Unified Multimodal Stack](/blog/omni-modal-stack). Picks up where the previous two posts left off and asks one question: what if the pretraining objective that gives you the best vision representations is not discriminative at all, but generation? Worked example throughout: Google DeepMind's [Vision Banana paper](https://arxiv.org/abs/2604.20329) (April 2026), which instruction-tunes Nano Banana Pro into a generalist that rivals or beats dedicated specialists on five vision-task families. About a 40-minute read.*

### 1. Where the trilogy left off

The first two posts in this series each closed on a piece of the same picture. [Post 1](/blog/unified-vision-stack) ended at C-RADIOv4: a single vision backbone trained from three teachers, producing dense features that could be read off by classification, segmentation, depth, or text-alignment heads. The encoder was the spinal cord; the heads were the lookup. [Post 2](/blog/omni-modal-stack) plugged that backbone into a four-modality agent: text decoder at the center, modality-specific encoders feeding it, token-budget tricks at the back to keep inference affordable. The decoder turned everything into language.

Both posts assumed the same shape. Image enters the front. Some encoder reads it. Some head, or some decoder, reads the encoder. The integers come out at the back of a softmax.

Vision Banana, the paper this post is about, asks what happens if you do the opposite. Put an image generator at the center. Train it on the usual generator's job (paint pictures from prompts). Then, at inference time, ask the same generator to paint perception. "Show me a segmentation mask for this street scene, where cars are red, sidewalks are blue, and sky is yellow." The model paints an RGB image. A short hash-table lookup at the very end converts each pixel's color back to a class label. The integers still come out at the back of the system. They just stop being the output of a softmax and start being the output of a `dict[(r, g, b)] -> class` lookup over the model's painted pixels.

The numerical evidence is on Vision Banana's own zero-shot benchmark tables. On the Cityscapes mIoU column of paper Table 2(a), [SAM 3](https://arxiv.org/abs/2511.16719) (Meta's most recent prompt-based segmentation foundation model, released November 2025) scores **0.652**. Vision Banana scores **0.699**, edging SAM 3 by 4.7 points. The non-zero-shot ceiling SegMan-L (in-domain training, included in the same chart for context) sits at **0.842**, well above either.

That column, and the depth and surface-normal columns next to it, are the throughline. We'll come back to them in every act.

## Act 1 — The puzzle

*Where the discriminative line ends and what a generator might do instead.*

### 2. Two ways to read what's in an image

The standard recipe for "read what's in this image and tell me at the pixel level" has been the same since the rise of the Vision Transformer. Hand the image to an encoder. The encoder produces a feature map, one feature vector per spatial patch. Hand the feature map to a small head: a linear layer for classification, a transposed-convolution stack for segmentation, a tiny MLP for depth. The head's output is a grid of integers (or floats), one per pixel. The integers come from the head's softmax (or the head's regression target).

What changes when you swap the encoder for a generator is the shape of the model's *output*. Instead of "image in, integers out," it's "image plus prompt in, image out." The decode step at the very end is what turns the painted pixels back into the integers the downstream task wanted. A class label is a hash-table lookup against the prompt's color spec; a depth value is a sample from a known false-color colormap; a normal vector is the (R, G, B) triple at that pixel, scaled to a unit sphere.

{/* TODO: Fig 1 (ParadigmFlip) - top half: discriminative pipeline (image -> encoder -> head -> mask integers via head softmax). Bottom half: generative pipeline (image + prompt JSON -> generator -> RGB output -> per-pixel decode lookup -> mask integers). Same input, same output, different middle. */}

The decisive move is which side of the system the lookup sits on. In a discriminator, the model emits the labels and the downstream code accepts them as is. In Vision Banana, the model emits a picture and the downstream code, which the user controls via the prompt, decides what each color means. The prompt is the lookup table.

This sounds like a small change. Three downstream consequences make it not.

The first is interface uniformity. Specialists, today, each emit a different shape: SAM 3's output is a grid of binary masks; [Depth Pro](https://arxiv.org/abs/2410.02073) emits a grid of floats; [DSINE](https://arxiv.org/abs/2403.00712) emits a grid of three-vectors. A pipeline that wants to use all three has to integrate three formats and three serving stacks. A pipeline built on Vision Banana integrates one: one model, one input contract, one output format (an RGB image). Whatever the downstream code is doing with the colors lives outside the model.

The second is class-set flexibility. A discriminator's head is fixed at training time. A SAM 3 mask doesn't natively carry "car / sidewalk / sky / pedestrian"; it carries whatever its training labels said. Vision Banana's class set is a JSON prompt at inference time: `{"car": "red", "sidewalk": "blue", ...}`. The same checkpoint, swap the prompt, get a different class set. We'll see in §11 the specific 2023 trick that made this work (random color mapping per training sample); for now, treat it as a property of the system.

The third is the question this post is really about. If the model can paint segmentation masks, depth maps, and surface-normal fields all as RGB images, and if the same model can hold up against the dedicated specialists on each of those benchmarks, then the encoder-plus-head template is not the only way to build a generalist vision backbone. Maybe the generator was the generalist all along.

That's the question. The next sections name the specialists.

### 3. The dedicated specialists

Vision Banana evaluates on five task families per the paper's experiments section: 2D understanding, broken into referring-expression segmentation, semantic segmentation, and instance segmentation; 3D understanding, broken into monocular metric depth and surface-normal estimation. Each task family has one or two recent specialist baselines that Vision Banana compares against on the corresponding benchmark.

For semantic segmentation, the canonical baseline is SAM 3 (released November 2025). SAM 3 is concept-prompted: the user supplies a short noun phrase (or an image exemplar) and the model returns a binary mask for everything in the image matching the prompt. The paper's stated headline is that SAM 3 doubles the accuracy of prior systems on prompt-based concept segmentation.

For instance segmentation, the comparison list includes DINO-X, OWLv2, and Gemini 2.5 (all recent open-vocabulary detectors). For referring-expression segmentation, HybridGL and SAM 3 paired with Gemini 2.5 Pro.

For monocular metric depth, the list runs Depth Pro (Apple, October 2024), [MoGe-2](https://arxiv.org/abs/2507.02546) (Microsoft, July 2025), and [UniK3D](https://arxiv.org/abs/2503.16591) (ETH and Politecnico di Milano, March 2025). [Depth Anything 3](https://arxiv.org/abs/2511.10647) (also November 2025) gets a separate comparison in paper Table 3.

For surface normals, [Marigold](https://arxiv.org/abs/2505.09358), [StableNormal](https://arxiv.org/abs/2406.16864), DSINE, and Lotus-2.

Each of these baselines is a recent, dedicated, well-understood specialist in its column. Each was trained on a per-task pipeline. And each one emits a different output format: SAM 3 returns binary mask grids; Depth Pro returns float depth maps; DSINE returns float normal vectors. None of them returns the same kind of object as any of the others.

{/* TODO: Fig 2 (SpecialistLineup) - five task-family columns across top with one or two representative specialists each, each with its output-format icon (mask grid for SAM 3, float depth for Depth Pro, float vector field for DSINE, etc.). Below them, a downward arrow to a single Vision Banana box that emits one output format (RGB image) for all five families. */}

That's the failure mode of the lineup. It is not that any single specialist is bad at its job; each is, by today's standards, very good. It's that wiring them together, or maintaining six of them in parallel, costs more than wiring or maintaining one. A modern computer-vision pipeline that wants depth and segmentation and normals is integrating three different model families with three different output contracts. Every per-model integration is a piece of glue code, a piece of inference infrastructure, and a piece of training-pipeline maintenance the team has to keep alive.

The implicit promise of any "generalist vision model" is to collapse all of those down into one model with one output format and one training pipeline. Vision Banana's claim is that the format that does the collapsing is RGB.

## Act 2 — The flip

*How Vision Banana parameterizes each task as RGB and what falls out on the benchmark tables.*

### 4. Meet Vision Banana

The substrate is Nano Banana Pro, which is the same model Google launched on November 20, 2025 as [Gemini 3 Pro Image](https://blog.google/innovation-and-ai/products/nano-banana-pro/). It runs in the Gemini app, the Gemini API, Google AI Studio, and Vertex AI. It is a deployed product, not a research artifact, and it has been generating user-prompted images at production scale for half a year by the time the Vision Banana paper goes up on arxiv.

Vision Banana is built by *instruction-tuning* Nano Banana Pro on a mixture: keep most of the original training-data mix (so the model continues to be a good image generator); add a small amount of vision-task data on top. The paper's exact phrasing for the mixture ratio is "We mix vision task data into Nano Banana Pro's own training mixture at a very low ratio." The vision-task data is whatever the paper's authors decided was a useful instruction-tuning corpus for the five task families: street scenes paired with prompted segmentation outputs, indoor photos paired with depth-as-false-color outputs, object photos paired with normals-as-RGB outputs, and so on.

The paper reports that, after this instruction tune, the base model's image-generation capabilities are preserved. You can still ask the post-tune Vision Banana to generate a picture of a banana on a beach, and you get a picture of a banana on a beach. The training mix protects the substrate from forgetting; the new vision-task data is light enough that it doesn't displace the original behavior.

{/* TODO: Fig 3 (VisionBananaArch) - Nano Banana Pro at the center as a deep stack with annotation "production generator, deployed via Gemini app / API / Vertex AI". A small instruction-tune layer wrapped around it. The vision-task data shown as a thin sliver of the training mix. Output is an RGB image. */}

The interesting question is what makes this work. The paper's hypothesis is the hard part: image-generation pretraining at internet scale gives a substrate already-suitable for downstream perception, and a tiny instruction-tune mix is therefore enough to read perception out of it. If that's right, then the bulk of Vision Banana's perception ability lives in the parts of the model that were trained on plain image generation, not in the small vision-task slice on top.

This is the paper's argument, not a settled causal claim. Vision Banana publishes no random-initialization ablation: there is no comparison run in which the same instruction-tuning recipe is applied to a non-pretrained generator and produces inferior numbers. The evidence the paper offers is the benchmark spread of §8: a model with a very light task tune holds up across five task families. That's circumstantial. It is consistent with "the substrate already had what perception needs," but it doesn't prove it. We'll stay honest about the difference whenever the prose touches that claim.

What the paper *can* point to, and what we'll spend the next three sections on, is the recipe: how each of the five task families gets parameterized as an RGB image. The recipe is mechanical, reproducible, and contains all the cleverness the paper is willing to publish in detail.

### 5. Segmentation as in-context coloring

Start with the simplest of the three reframings. Vision Banana does semantic segmentation by being told, per inference, what color to use for each class. The user supplies a JSON prompt that maps class names to color names: `{"cat": "red", "lock": "pink"}`. The model paints an RGB image where each pixel adopts the color of whichever class the model thinks that pixel belongs to. A short post-processing pass walks the painted output and assigns each pixel to a class by matching the painted color against the prompt's keys.

The paper's exact phrasing on the inference contract is: "we assign pixels to classes by matching its color according to the prompt." On the prompt itself: "instruct Vision Banana to produce segmentation masks for only one class, allowing the model to dynamically assign colors to different instances." The first phrasing covers the per-class-color setup; the second covers an instance-segmentation extension where the model picks the colors per instance.

The decode step is, mechanically, a hash-table lookup. The prompt's `{"car": "red", "sidewalk": "blue", "sky": "yellow", ...}` gives you a `{(255, 0, 0): "car", (0, 0, 255): "sidewalk", (255, 255, 0): "sky", ...}` lookup table. Walk the painted RGB image pixel by pixel; for each pixel, find the closest entry in the table by RGB distance; that entry's value is the class label. Output is a per-pixel grid of class labels, the same kind of object SAM 3 returns.

{/* TODO: Fig 4 (SegmentationAsColoring) - Input image of a street scene; JSON prompt to the right (`{"car": "red", "sidewalk": "blue", "sky": "yellow"}`); output: RGB-painted image with car/sidewalk/sky as those distinct colors; decode arrow with the lookup table; final mask of class labels. Figcaption disclaimer: drawn schematically; the matrix backs aggregate Cityscapes mIoU, not this specific image. */}

This is the recipe behind the throughline number. Vision Banana's 0.699 zero-shot Cityscapes mIoU on paper Table 2(a) is what happens when you take a Cityscapes test image, build a JSON prompt covering all 19 Cityscapes classes (each mapped to a distinct RGB color), feed both to Vision Banana, run the painted output through the color-distance decode, and score the resulting per-pixel labels against the Cityscapes ground truth. The model never saw the Cityscapes 19-class palette during instruction tuning; the prompt is what told it which 19 categories to discriminate this time.

A discriminative segmenter cannot do that. SAM 3's class set is decided at training time. To run SAM 3 on Cityscapes you have to either retrain its head on Cityscapes labels (no longer zero-shot) or accept SAM 3's native class behavior and translate the output. Vision Banana's class set lives in the prompt the user types at inference. Swap the prompt, get a different class set. The reason this works at all is a 2023 trick from the Painter team that we'll get to in §11.

For now, the takeaway is mechanical. Segmentation, in Vision Banana's world, is image generation with a colored-class prompt and a per-pixel color-distance decode at the end. The mask is just a picture; the labels are the colors.

### 6. Depth as power-transformed false-color

Depth is harder than segmentation. A class label is a small finite set of options: car, sidewalk, sky. A depth value is a real number in some unbounded range, typically meters from camera. A flat color map breaks down as soon as the scene has both close objects (a hand at the edge of the frame) and distant ones (a building on the horizon).

Vision Banana's depth parameterization is the cleverest of the three. The paper's words: "we instruct the model to output a carefully constructed false-color visualization of depth values…using those curved distances to produce a false-color visualization." The mechanism, decoded from the methods section: take the raw depth value at each pixel, apply a power transform with exponent λ=−3 (so that close depths get stretched out and far depths get compressed; the inverse-cube emphasis is what makes the colormap legible across a wide dynamic range), and then map the transformed value onto a piecewise-linear path that walks the edges of the RGB cube.

The "edges of the RGB cube" idea is worth a paragraph. The RGB color space is a 3D cube whose corners are the eight pure colors: black, red, green, blue, yellow, magenta, cyan, white. The cube has twelve edges. If you walk a path along those edges, you get a 1D parametrization of color that visits a wide range of hues without doubling back. (You can imagine walking from black along the red edge to red, then red→yellow→green→cyan→blue→magenta→white, or any other Hamilton-path-like route.) Vision Banana's depth colormap uses such a path: the transformed depth value, normalized to the unit interval, is the path parameter; the color at the corresponding point on the path is what gets painted at that pixel.

{/* TODO: Fig 5 (DepthAsFalseColor) - three panels: (a) input photo of a room or street; (b) the power-transform curve plotted as input depth (meters) -> output color-position-along-cube-edge (0..1), with the inverse-cube curvature visible; (c) the resulting false-color depth image, showing the cube-edge palette in action. */}

The decode step is the colormap lookup in reverse. Walk the painted output pixel by pixel; for each pixel, find the closest point on the RGB-cube path; back out the path parameter; invert the power transform; you get back a depth value in meters.

The throughline numbers fall out of this recipe. On the project-page six-benchmark depth chart, Vision Banana scores 0.882 δ₁ (the fraction of pixels whose predicted depth is within 25% of the ground truth), against UniK3D at 0.823, MoGe-2 at 0.802, and Depth Pro at 0.715. (The chart does not include either Depth Anything V2 or [Depth Anything V3](https://arxiv.org/abs/2511.10647).) On the paper's Table 3, which reports an average over four specific datasets where Depth Anything 3 was also evaluated (NYU, ETH3D, DIODE, KITTI), Vision Banana scores 0.929 against DA3's 0.918. A 1.1-point edge over the strongest specialist VB compares against on the four-dataset overlap; a 5.9-point edge over the strongest specialist on the broader six-benchmark chart; and a number every reader can trace back to the depth false-color recipe in this section.

The "depth map" in modern computer vision papers is usually presented as a grayscale image (darker = closer; lighter = farther) or as a colormap visualization for human readers. In Vision Banana, the false-color visualization *is* the model's output. The model doesn't compute depth and then visualize it; the colormap is the parameterization the model is trained to predict.

### 7. Surface normals as direct xyz→RGB

Normals are the simplest of the three reframings. A surface normal at a pixel is a unit vector in 3D, which is to say three numbers (x, y, z) with x² + y² + z² = 1. RGB is also three numbers. The map between them is no transform at all: take the unit vector's components, shift them from the [-1, +1] range to [0, 255], and call those the R, G, B channels.

Or more directly, in the paper's own example: "the directional vector components map directly to RGB channels: Facing Left (−1, 0, 0): Encoded as Pinkish Red…" Facing left means x = −1, which after the shift is R = 0; the "Pinkish Red" name is a convention. The point is that the encoding is deterministic, lossless, and reversible. There is no learned colormap. The model paints a normal field as if it were an RGB image, and the decode is a fixed affine transform per pixel.

{/* TODO: Fig 6 (NormalsAsXYZ) - left panel: a 3D unit sphere with axis labels (X right, Y up, Z out of screen). Right panel: the RGB cube with the same orientation. Arrows from sphere positions to cube positions: (-1, 0, 0) -> pinkish red; (0, 1, 0) -> green; (0, 0, 1) -> blue; etc. Below, the same color encoding applied to a normal map of a small object so the reader sees the mapping live. */}

If you want a one-line intuition for why this works: a unit-vector field is the geometry of the world's surfaces, expressed as direction. RGB is also a 3D space whose "natural" interpretation is whatever the model decides to make of it. The Vision Banana training data tells the model "this surface direction in 3D corresponds to this RGB triple in the output picture." The model treats the picture as the surface direction, end to end, no intermediate representation needed.

The throughline number on the surface-normal column is 15.549° mean angular error, against Lotus-2 at 16.558°, DSINE at 17.017°, StableNormal at 17.168°, and Marigold at 19.606° on the project-page three-benchmark average. (Vision Banana's paper Table 1 reports a separate four-dataset normals average where VB scores 18.928° against Lotus-2's 19.642°. That's a different eval slice with different numbers; the post cites each in its own context.) A 1.0° improvement over the previous best, which doesn't sound like much until you remember that the unit is "average angular error in 3D direction across millions of pixels" and a 1° improvement is real.

The pattern across §§5–7 is now visible. Each task family gets a different parameterization, but the parameterizations share a structure: pick a way to encode the task's output as an RGB image; train the generator on input/output pairs in that encoding; at inference, run the input through the model and decode the painted output. Segmentation uses class-to-color JSON. Depth uses a power-transformed walk along the RGB cube's edges. Normals use the trivial xyz-to-RGB shift. Three task families, three different colormaps, one model.

### 8. The benchmark spread, honestly

Now we can lay out the full benchmark picture in one place. Vision Banana evaluates on five task families, each with its own tables. The paper highlights four of those tables as load-bearing comparisons against named recent specialists; we'll work through each.

**Zero-shot Cityscapes mIoU** (paper Table 2(a), semantic segmentation). Vision Banana 0.699; SAM 3 0.652; X-Decoder 0.520; OpenSeeD 0.478; APE-D 0.442. The non-zero-shot ceiling, included in the same chart for context, is SegMan-L at 0.842. Vision Banana's own paper sentence: "Vision Banana surpasses SAM 3 by 4.7 points in mIoU." That's the headline zero-shot number. The non-zero-shot ceiling sits 14.3 points above zero-shot Vision Banana, and 19 points above SAM 3, so a specialist that gets to fine-tune on Cityscapes labels still wins its own benchmark by a wide margin. Vision Banana wins the *zero-shot* contest, by a clear but modest 4.7-point edge.

**Project-page six-benchmark metric depth δ₁** (the average of δ₁ accuracy across NYU, ETH3D, DIODE, KITTI, plus two more datasets the paper aggregates; see [the project page](https://vision-banana.github.io/) for the full list). Vision Banana 0.882; UniK3D 0.823; MoGe-2 0.802; Depth Pro 0.715. A 5.9-point edge over the strongest specialist on the chart. Notable: the chart includes neither Depth Anything V2 nor Depth Anything 3, which is why the post can't claim "Vision Banana beats the Depth Anything line" from this chart alone.

**Paper Table 3 four-dataset metric depth δ₁** (NYU, ETH3D, DIODE, KITTI, the same four where Depth Anything 3 was evaluated). Vision Banana 0.929; Depth Anything 3 0.918. The 1.1-point edge here is the only direct VB-vs-DA3 comparison the paper offers. The paper's exact phrasing: "Vision Banana achieves an average δ₁ accuracy of 0.882, outperforming…Depth Anything V3 on average across the four datasets (NYU, ETH3D, DIODE, KITTI) on which it was evaluated (0.929 v.s. 0.918)." Note that 0.882 is the broader six-dataset average from the project-page chart; 0.929 is the narrower four-dataset average where DA3 also reported. Two different averages, two different stories, both in the same paper.

**Project-page three-benchmark surface-normal mean angular error**. Vision Banana 15.549°; Lotus-2 16.558°; DSINE 17.017°; StableNormal 17.168°; Marigold 19.606°. A 1.0° edge over Lotus-2 on this aggregate. Paper Table 1 reports a separate four-dataset normals average where VB scores 18.928° against Lotus-2's 19.642°. Different slice, different absolute numbers, the same direction of result.

**Instance and referring-expression segmentation** round out the five families with similar shapes: VB scores 0.661 pmF1 on the SA-Co/Gold instance-segmentation benchmark against Gemini 2.5's 0.540 and DINO-X's 0.552; 0.794 cIoU on RefCOCOg-val against the strongest paired-baseline 0.738 (SAM 3 + Gemini 2.5 Pro). The numbers are competitive and consistent with the rest of the table; we'll mostly leave these in the references for readers who want to chase them.

What does this spread say? It says that one model, lightly tuned on top of an off-the-shelf production image generator, holds up against the most recent dedicated specialists across five disparate task families. It does not say that Vision Banana destroys those specialists. The deltas are real but modest: 4.7 points on Cityscapes, 1.1 points over Depth Anything 3, 5.9 points over UniK3D, 1.0° over Lotus-2. Specialists trained in-domain (the SegMan-L ceiling) still win their column when they're allowed to. Vision Banana's claim is the existence of one single model whose zero-shot numbers cluster near the top across all five families at once. That's a different kind of win.

The honest framing is "rivals or beats specialists," not "crushes them." Posts that overstate this risk losing the actual interesting claim, which is the existence proof: a generative-pretraining substrate, plus a light task-data tune, gets you a generalist that's competitive across a wide spread of dense-prediction work.

The spread holds up. But the paper publishes no random-initialization ablation. There is no controlled experiment showing that the same instruction-tuning recipe applied to a non-pretrained generator produces inferior numbers. So the question Act 3 has to answer is the obvious one: why would a model trained only to paint pictures already have the representations needed for dense prediction, before any vision-task tuning kicks in? The paper's hypothesis is that image-generation pretraining gives a substrate already-suitable for perception. Act 3 traces the five-year arc that made that hypothesis plausible enough to test.
