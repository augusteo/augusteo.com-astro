*A sequel to [The Unified Vision Stack](/blog/unified-vision-stack) and [The Unified Multimodal Stack](/blog/omni-modal-stack). Picks up where the previous two posts left off and asks one question: what if the pretraining objective that gives you the best vision representations is not discriminative at all, but generation? Worked example throughout: Google DeepMind's [Vision Banana paper](https://arxiv.org/abs/2604.20329) (April 2026), which instruction-tunes Nano Banana Pro into a generalist that rivals or beats dedicated specialists on five vision-task families. About a 40-minute read.*

### 1. Where the trilogy left off

The first two posts in this series each closed on a piece of the same picture. [Post 1](/blog/unified-vision-stack) ended at C-RADIOv4: a single vision backbone trained from three teachers, producing dense features that could be read off by classification, segmentation, depth, or text-alignment heads. The encoder was the spinal cord; the heads were the lookup. [Post 2](/blog/omni-modal-stack) plugged that backbone into a four-modality agent: text decoder at the center, modality-specific encoders feeding it, token-budget tricks at the back to keep inference affordable. The decoder turned everything into language.

Both posts assumed the same shape. Image enters the front. Some encoder reads it. Some head, or some decoder, reads the encoder. The integers come out at the back of a softmax.

Vision Banana, the paper this post is about, asks what happens if you do the opposite. Put an image generator at the center. Train it on the usual generator's job (paint pictures from prompts). Then, at inference time, ask the same generator to paint perception. "Show me a segmentation mask for this street scene, where cars are red, sidewalks are blue, and sky is yellow." The model paints an RGB image. A short hash-table lookup at the very end converts each pixel's color back to a class label. The integers still come out at the back of the system. They just stop being the output of a softmax and start being the output of a `dict[(r, g, b)] -> class` lookup over the model's painted pixels.

The numerical evidence is on Vision Banana's own zero-shot benchmark tables. On the Cityscapes mIoU column of paper Table 2(a), [SAM 3](https://arxiv.org/abs/2511.16719) (Meta's most recent prompt-based segmentation foundation model, released November 2025) scores **0.652**. Vision Banana scores **0.699**, edging SAM 3 by 4.7 points. The non-zero-shot ceiling SegMan-L (in-domain training, included in the same chart for context) sits at **0.842**, well above either.

That column, and the depth and surface-normal columns next to it, are the throughline. We'll come back to them in every act.

## Act 1 — The puzzle

*Where the discriminative line ends and what a generator might do instead.*

### 2. Two ways to read what's in an image

The standard recipe for "read what's in this image and tell me at the pixel level" has been the same since the rise of the Vision Transformer. Hand the image to an encoder. The encoder produces a feature map, one feature vector per spatial patch. Hand the feature map to a small head: a linear layer for classification, a transposed-convolution stack for segmentation, a tiny MLP for depth. The head's output is a grid of integers (or floats), one per pixel. The integers come from the head's softmax (or the head's regression target).

What changes when you swap the encoder for a generator is the shape of the model's *output*. Instead of "image in, integers out," it's "image plus prompt in, image out." The decode step at the very end is what turns the painted pixels back into the integers the downstream task wanted. A class label is a hash-table lookup against the prompt's color spec; a depth value is a sample from a known false-color colormap; a normal vector is the (R, G, B) triple at that pixel, scaled to a unit sphere.

The decisive move is which side of the system the lookup sits on. In a discriminator, the model emits the labels and the downstream code accepts them as is. In Vision Banana, the model emits a picture and the downstream code, which the user controls via the prompt, decides what each color means. The prompt is the lookup table.

This sounds like a small change. Three downstream consequences make it not.

The first is interface uniformity. Specialists, today, each emit a different shape: SAM 3's output is a grid of binary masks; [Depth Pro](https://arxiv.org/abs/2410.02073) emits a grid of floats; [DSINE](https://arxiv.org/abs/2403.00712) emits a grid of three-vectors. A pipeline that wants to use all three has to integrate three formats and three serving stacks. A pipeline built on Vision Banana integrates one: one model, one input contract, one output format (an RGB image). Whatever the downstream code is doing with the colors lives outside the model.

The second is class-set flexibility. A discriminator's head is fixed at training time. A SAM 3 mask doesn't natively carry "car / sidewalk / sky / pedestrian"; it carries whatever its training labels said. Vision Banana's class set is a JSON prompt at inference time: `{"car": "red", "sidewalk": "blue", ...}`. The same checkpoint, swap the prompt, get a different class set. We'll see in §11 the specific 2023 trick that made this work (random color mapping per training sample); for now, treat it as a property of the system.

The third is the question this post is really about. If the model can paint segmentation masks, depth maps, and surface-normal fields all as RGB images, and if the same model can hold up against the dedicated specialists on each of those benchmarks, then the encoder-plus-head template is not the only way to build a generalist vision backbone. Maybe the generator was the generalist all along.

That's the question. The next sections name the specialists.

### 3. The dedicated specialists

Vision Banana evaluates on five task families per the paper's experiments section: 2D understanding, broken into referring-expression segmentation, semantic segmentation, and instance segmentation; 3D understanding, broken into monocular metric depth and surface-normal estimation. Each task family has one or two recent specialist baselines that Vision Banana compares against on the corresponding benchmark.

For semantic segmentation, the canonical baseline is SAM 3 (released November 2025). SAM 3 is concept-prompted: the user supplies a short noun phrase (or an image exemplar) and the model returns a binary mask for everything in the image matching the prompt. The paper's stated headline is that SAM 3 doubles the accuracy of prior systems on prompt-based concept segmentation.

For instance segmentation, the comparison list includes DINO-X, OWLv2, and Gemini 2.5 (all recent open-vocabulary detectors). For referring-expression segmentation, HybridGL and SAM 3 paired with Gemini 2.5 Pro.

For monocular metric depth, the list runs Depth Pro (Apple, October 2024), [MoGe-2](https://arxiv.org/abs/2507.02546) (Microsoft, July 2025), and [UniK3D](https://arxiv.org/abs/2503.16591) (ETH and Politecnico di Milano, March 2025). [Depth Anything 3](https://arxiv.org/abs/2511.10647) (also November 2025) gets a separate comparison in paper Table 3.

For surface normals, [Marigold](https://arxiv.org/abs/2505.09358), [StableNormal](https://arxiv.org/abs/2406.16864), DSINE, and Lotus-2.

Each of these baselines is a recent, dedicated, well-understood specialist in its column. Each was trained on a per-task pipeline. And each one emits a different output format: SAM 3 returns binary mask grids; Depth Pro returns float depth maps; DSINE returns float normal vectors. None of them returns the same kind of object as any of the others.

That's the failure mode of the lineup. It is not that any single specialist is bad at its job; each is, by today's standards, very good. It's that wiring them together, or maintaining six of them in parallel, costs more than wiring or maintaining one. A modern computer-vision pipeline that wants depth and segmentation and normals is integrating three different model families with three different output contracts. Every per-model integration is a piece of glue code, a piece of inference infrastructure, and a piece of training-pipeline maintenance the team has to keep alive.

The implicit promise of any "generalist vision model" is to collapse all of those down into one model with one output format and one training pipeline. Vision Banana's claim is that the format that does the collapsing is RGB.

### 4. Meet Vision Banana

The substrate is Nano Banana Pro, which is the same model Google launched on November 20, 2025 as [Gemini 3 Pro Image](https://blog.google/innovation-and-ai/products/nano-banana-pro/). It runs in the Gemini app, the Gemini API, Google AI Studio, and Vertex AI. It is a deployed product, not a research artifact, and it has been generating user-prompted images at production scale for half a year by the time the Vision Banana paper goes up on arxiv.

Vision Banana is built by *instruction-tuning* Nano Banana Pro on a mixture: keep most of the original training-data mix (so the model continues to be a good image generator); add a small amount of vision-task data on top. The paper's exact phrasing for the mixture ratio is "We mix vision task data into Nano Banana Pro's own training mixture at a very low ratio." The vision-task data is whatever the paper's authors decided was a useful instruction-tuning corpus for the five task families: street scenes paired with prompted segmentation outputs, indoor photos paired with depth-as-false-color outputs, object photos paired with normals-as-RGB outputs, and so on.

The paper reports that, after this instruction tune, the base model's image-generation capabilities are preserved. You can still ask the post-tune Vision Banana to generate a picture of a banana on a beach, and you get a picture of a banana on a beach. The training mix protects the substrate from forgetting; the new vision-task data is light enough that it doesn't displace the original behavior.

The interesting question is what makes this work. The paper's hypothesis is the hard part: image-generation pretraining at internet scale gives a substrate already-suitable for downstream perception, and a tiny instruction-tune mix is therefore enough to read perception out of it. If that's right, then the bulk of Vision Banana's perception ability lives in the parts of the model that were trained on plain image generation, not in the small vision-task slice on top.

This is the paper's argument, not a settled causal claim. Vision Banana publishes no random-initialization ablation: there is no comparison run in which the same instruction-tuning recipe is applied to a non-pretrained generator and produces inferior numbers. The evidence the paper offers is the benchmark spread of §8: a model with a very light task tune holds up across five task families. That's circumstantial. It is consistent with "the substrate already had what perception needs," but it doesn't prove it. We'll stay honest about the difference whenever the prose touches that claim.

What the paper *can* point to, and what we'll spend the next three sections on, is the recipe: how each of the five task families gets parameterized as an RGB image. The recipe is mechanical, reproducible, and contains all the cleverness the paper is willing to publish in detail.

### 5. Segmentation as in-context coloring

Start with the simplest of the three reframings. Vision Banana does semantic segmentation by being told, per inference, what color to use for each class. The user supplies a JSON prompt that maps class names to color names: `{"cat": "red", "lock": "pink"}`. The model paints an RGB image where each pixel adopts the color of whichever class the model thinks that pixel belongs to. A short post-processing pass walks the painted output and assigns each pixel to a class by matching the painted color against the prompt's keys.

The paper's exact phrasing on the inference contract is: "we assign pixels to classes by matching its color according to the prompt." On the prompt itself: "instruct Vision Banana to produce segmentation masks for only one class, allowing the model to dynamically assign colors to different instances." The first phrasing covers the per-class-color setup; the second covers an instance-segmentation extension where the model picks the colors per instance.

The decode step is, mechanically, a hash-table lookup. The prompt's `{"car": "red", "sidewalk": "blue", "sky": "yellow", ...}` gives you a `{(255, 0, 0): "car", (0, 0, 255): "sidewalk", (255, 255, 0): "sky", ...}` lookup table. Walk the painted RGB image pixel by pixel; for each pixel, find the closest entry in the table by RGB distance; that entry's value is the class label. Output is a per-pixel grid of class labels, the same kind of object SAM 3 returns.

The model never saw the Cityscapes 19-class palette during instruction tuning; the prompt is what told it which 19 categories to discriminate this time.

A discriminative segmenter cannot do that. SAM 3's class set is decided at training time. To run SAM 3 on Cityscapes you have to either retrain its head on Cityscapes labels (no longer zero-shot) or accept SAM 3's native class behavior and translate the output. Vision Banana's class set lives in the prompt the user types at inference. Swap the prompt, get a different class set. The reason this works at all is a 2023 trick from the Painter team that we'll get to in §11.

For now, the takeaway is mechanical. Segmentation, in Vision Banana's world, is image generation with a colored-class prompt and a per-pixel color-distance decode at the end. The mask is just a picture; the labels are the colors.

### 6. Depth as power-transformed false-color

Depth is harder than segmentation. A class label is a small finite set of options: car, sidewalk, sky. A depth value is a real number in some unbounded range, typically meters from camera. A flat color map breaks down as soon as the scene has both close objects (a hand at the edge of the frame) and distant ones (a building on the horizon).

Vision Banana's depth parameterization is the cleverest of the three. The paper's words: "we instruct the model to output a carefully constructed false-color visualization of depth values…using those curved distances to produce a false-color visualization." The mechanism, decoded from the methods section: take the raw depth value at each pixel, apply a power transform with exponent λ=−3 (so that close depths get stretched out and far depths get compressed; the inverse-cube emphasis is what makes the colormap legible across a wide dynamic range), and then map the transformed value onto a piecewise-linear path that walks the edges of the RGB cube.

The "edges of the RGB cube" idea is worth a paragraph. The RGB color space is a 3D cube whose corners are the eight pure colors: black, red, green, blue, yellow, magenta, cyan, white. The cube has twelve edges. If you walk a path along those edges, you get a 1D parametrization of color that visits a wide range of hues without doubling back. (You can imagine walking from black along the red edge to red, then red→yellow→green→cyan→blue→magenta→white, or any other Hamilton-path-like route.) Vision Banana's depth colormap uses such a path: the transformed depth value, normalized to the unit interval, is the path parameter; the color at the corresponding point on the path is what gets painted at that pixel.

The decode step is the colormap lookup in reverse. Walk the painted output pixel by pixel; for each pixel, find the closest point on the RGB-cube path; back out the path parameter; invert the power transform; you get back a depth value in meters.

The "depth map" in modern computer vision papers is usually presented as a grayscale image (darker = closer; lighter = farther) or as a colormap visualization for human readers. In Vision Banana, the false-color visualization *is* the model's output. The model doesn't compute depth and then visualize it; the colormap is the parameterization the model is trained to predict.

### 7. Surface normals as direct xyz→RGB

Normals are the simplest of the three reframings. A surface normal at a pixel is a unit vector in 3D, which is to say three numbers (x, y, z) with x² + y² + z² = 1. RGB is also three numbers. The map between them is no transform at all: take the unit vector's components, shift them from the [-1, +1] range to [0, 255], and call those the R, G, B channels.

Or more directly, in the paper's own example: "the directional vector components map directly to RGB channels: Facing Left (−1, 0, 0): Encoded as Pinkish Red…" Facing left means x = −1, which after the shift is R = 0; the "Pinkish Red" name is a convention. The point is that the encoding is deterministic, lossless, and reversible. There is no learned colormap. The model paints a normal field as if it were an RGB image, and the decode is a fixed affine transform per pixel.

If you want a one-line intuition for why this works: a unit-vector field is the geometry of the world's surfaces, expressed as direction. RGB is also a 3D space whose "natural" interpretation is whatever the model decides to make of it. The Vision Banana training data tells the model "this surface direction in 3D corresponds to this RGB triple in the output picture." The model treats the picture as the surface direction, end to end, no intermediate representation needed.

The throughline number on the surface-normal column is 15.549° mean angular error, against Lotus-2 at 16.558°, DSINE at 17.017°, StableNormal at 17.168°, and Marigold at 19.606° on the project-page three-benchmark average. (Vision Banana's paper Table 1 reports a separate four-dataset normals average where VB scores 18.928° against Lotus-2's 19.642°. That's a different eval slice with different numbers; the post cites each in its own context.) A 1.0° improvement over the previous best, which doesn't sound like much until you remember that the unit is "average angular error in 3D direction across millions of pixels" and a 1° improvement is real.

The pattern across §§5–7 is now visible. Each task family gets a different parameterization, but the parameterizations share a structure: pick a way to encode the task's output as an RGB image; train the generator on input/output pairs in that encoding; at inference, run the input through the model and decode the painted output. Segmentation uses class-to-color JSON. Depth uses a power-transformed walk along the RGB cube's edges. Normals use the trivial xyz-to-RGB shift. Three task families, three different colormaps, one model.

### 8. The benchmark spread, honestly

Now we can lay out the full benchmark picture in one place. Vision Banana evaluates on five task families, each with its own tables. The paper highlights four of those tables as load-bearing comparisons against named recent specialists; we'll work through each.

**Zero-shot Cityscapes mIoU** (paper Table 2(a), semantic segmentation). Vision Banana 0.699; SAM 3 0.652; X-Decoder 0.520; OpenSeeD 0.478; APE-D 0.442. The non-zero-shot ceiling, included in the same chart for context, is SegMan-L at 0.842. Vision Banana's own paper sentence: "Vision Banana surpasses SAM 3 by 4.7 points in mIoU." That's the headline zero-shot number. The non-zero-shot ceiling sits 14.3 points above zero-shot Vision Banana, and 19 points above SAM 3, so a specialist that gets to fine-tune on Cityscapes labels still wins its own benchmark by a wide margin. Vision Banana wins the *zero-shot* contest, by a clear but modest 4.7-point edge.

**Project-page six-benchmark metric depth δ₁** (the average of δ₁ accuracy across NYU, ETH3D, DIODE, KITTI, plus two more datasets the paper aggregates; see [the project page](https://vision-banana.github.io/) for the full list). Vision Banana 0.882; UniK3D 0.823; MoGe-2 0.802; Depth Pro 0.715. A 5.9-point edge over the strongest specialist on the chart. Notable: the chart includes neither Depth Anything V2 nor Depth Anything 3, which is why the post can't claim "Vision Banana beats the Depth Anything line" from this chart alone.

**Paper Table 3 four-dataset metric depth δ₁** (NYU, ETH3D, DIODE, KITTI, the same four where Depth Anything 3 was evaluated). Vision Banana 0.929; Depth Anything 3 0.918. The 1.1-point edge here is the only direct VB-vs-DA3 comparison the paper offers. The paper's exact phrasing: "Vision Banana achieves an average δ₁ accuracy of 0.882, outperforming…Depth Anything V3 on average across the four datasets (NYU, ETH3D, DIODE, KITTI) on which it was evaluated (0.929 v.s. 0.918)." Note that 0.882 is the broader six-dataset average from the project-page chart; 0.929 is the narrower four-dataset average where DA3 also reported. **Project-page three-benchmark surface-normal mean angular error**. Vision Banana 15.549°; Lotus-2 16.558°; DSINE 17.017°; StableNormal 17.168°; Marigold 19.606°. What does this spread say? It says that one model, lightly tuned on top of an off-the-shelf production image generator, holds up against the most recent dedicated specialists across five disparate task families. It does not say that Vision Banana destroys those specialists. The deltas are real but modest: 4.7 points on Cityscapes, 1.1 points over Depth Anything 3, 5.9 points over UniK3D, 1.0° over Lotus-2. Specialists trained in-domain (the SegMan-L ceiling) still win their column when they're allowed to. Vision Banana's claim is the existence of one single model whose zero-shot numbers cluster near the top across all five families at once. That's a different kind of win.

The honest framing is "rivals or beats specialists," not "crushes them." Posts that overstate this risk losing the actual interesting claim, which is the existence proof: a generative-pretraining substrate, plus a light task-data tune, gets you a generalist that's competitive across a wide spread of dense-prediction work.

The spread holds up. But the paper publishes no random-initialization ablation. There is no controlled experiment showing that the same instruction-tuning recipe applied to a non-pretrained generator produces inferior numbers. So the question Act 3 has to answer is the obvious one: why would a model trained only to paint pictures already have the representations needed for dense prediction, before any vision-task tuning kicks in? The paper's hypothesis is that image-generation pretraining gives a substrate already-suitable for perception. Act 3 traces the five-year arc that made that hypothesis plausible enough to test.

## Act 3 — Why it works

*The five-year arc that made image-generation pretraining a candidate for the substrate of perception.*

### 9. MAE (2021): reconstruction as pretraining

The starting rung of the arc is [Masked Autoencoders Are Scalable Vision Learners](https://arxiv.org/abs/2111.06377), the November 2021 paper from Kaiming He, Xinlei Chen, Saining Xie, Yanghao Li, Piotr Dollár, and Ross Girshick. The recipe: take a Vision Transformer, mask a high fraction of its input patches (75% in the original), train an asymmetric encoder–decoder to reconstruct the missing pixels. The asymmetry is part of the trick. The encoder sees only the visible 25%; the decoder, much smaller than the encoder, sees the visible patch tokens plus learnable mask tokens for the gaps and predicts pixel values for the masked positions.

The paper's own framing: "We mask random patches of the input image and reconstruct the missing pixels…an asymmetric encoder-decoder design that is key to the method…accelerate training (by 3x or more) and improve accuracy."

Two things make this rung load-bearing for the rest of the story.

The first is the objective. MAE's pretraining loss is, mechanically, image reconstruction. The model is rewarded for producing pixel values that match the held-out patches. This was sometimes presented as "self-supervised learning" (a label that emphasizes the absence of human-supplied class labels) and sometimes as "masked image modeling" (a label that emphasizes the borrowed BERT-style masking). The honest description is that MAE is trained to *generate* the missing parts of an image, conditioned on the visible parts. Whether you call that self-supervised or generative is a matter of which side of the room you're standing on.

The second is the result. MAE pretraining produced encoders whose features were strong enough to fine-tune on classification, segmentation, and detection benchmarks at the time, often outperforming contrastive-pretrained encoders of the same size. Pretraining on reconstruction, in other words, was not in tension with downstream perception; it might even have been better for it.

{/* TODO: Fig 8 (MAEDiagram) - standard MAE schematic: image with random patches masked (gray rectangles); encoder sees visible patches only; decoder sees visible-patch tokens plus learnable mask tokens; decoder reconstructs full image (RGB pixels at the masked positions). Mirrors the DINOv3 figure shape from post 1 for visual continuity. */}

What MAE did not tell us, as of 2021, was what happens at the *output side*. The pretraining objective was reconstruction, and the downstream evaluation was on encoder features (with task-specific heads attached after pretraining was done). The path from "reconstruction is the pretraining" to "the reconstructed image itself is useful for perception" is what the next two papers, Painter and SegGPT, build over the next eighteen months.

What's worth pointing out before moving on: Kaiming He and Saining Xie are co-authors on MAE in 2021, and they are co-authors on Vision Banana in 2026. Two of the twenty-five names on the Vision Banana author list are the same names that put MAE on arxiv five years earlier. The arc this section traces is not a coincidence. It's a research program that has been pushing on the same set of ideas for half a decade.

### 10. Painter (2022): output space as image

A year later, Xinlong Wang and colleagues at Beijing Academy of Artificial Intelligence published [Painter](https://arxiv.org/abs/2212.02499). Painter is the rung where the *output* of every vision task becomes an image, full stop, with no per-task head retrofitted on the back.

The paper's own description: "We propose Painter, a generalist vision model by redefining the output of core vision tasks as images…Our training process is extremely simple, which performs standard masked image modeling on the stitch of input and output image pairs."

The "stitch" idea is what makes the recipe work. Take an input image and its output for some task (a segmentation mask drawn as colors, a depth map drawn as a colormap, an edge map drawn as black lines on white). Stitch the two side by side into a single wider image. Apply the MAE-style masked-image-modeling objective to the stitch: mask random patches of the stitched image, train the encoder–decoder to reconstruct them. At training time, the masked patches are sometimes in the input half and sometimes in the output half; the model learns to fill in either. At inference time, you supply the input half plus a *blank* output half; the model fills the blank.

The downstream consequence is enormous, but it took until Painter to spell out. Once the output of every task is an image, the architecture is identical across tasks: same encoder, same decoder, same loss, same training pipeline. The only thing that changes per task is the input/output stitch convention. Segmentation: input photo stitched to colored-mask. Depth: input photo stitched to depth colormap. The model doesn't need to know which task it's doing; the stitch convention encodes that for it.

{/* TODO: Fig 9 (PainterStitched) - input photo (left half) stitched horizontally to its output (right half) - segmentation map drawn as colors, or depth map drawn as colormap. A diagonal mask crossing both halves shows random patches dropped. The model trained to fill in the masked pixels. */}

The throughline thread runs through Painter directly. Vision Banana's segmentation column inherits Painter's contract: the output of segmentation is an image, which means a generative model can paint it, which means the same model that paints rest-of-the-world images can be repurposed for the segmentation column without changing what the model emits. The 0.699 mIoU of §5 sits downstream of "the output is an image" as a paradigm choice, and that paradigm choice is Painter's.

What Painter did not, by itself, do is solve the class-flexibility problem. A Painter trained on one segmentation dataset's class palette could not, at inference, switch to a different dataset's class palette without retraining. The output-as-image contract was there; the in-context, prompt-based class-set flexibility was not. That's the next paper's contribution.

### 11. SegGPT (2023): random color mapping per sample

Painter's class-flexibility problem was real. If you trained Painter on Cityscapes labels (where the segmentation map paints "car" red and "sky" blue with a fixed color-to-class palette), the model learned that "red means car." At inference, switching to a different dataset with a different palette meant retraining the segmentation behavior.

The Wang et al. team's follow-up the next year, [SegGPT](https://arxiv.org/abs/2304.03284), fixed this with a small training-time intervention. Instead of using a fixed color-to-class palette across the training corpus, SegGPT *randomly recolors* the segmentation masks. Every training example gets its own arbitrary mapping from class names to colors. The model never sees a stable "red means car" pairing; the same image can have its cars painted red one batch and green the next.

The paper's own description: "the training uses an in-context coloring problem with random color mapping for each data sample."

What this does to the model's representations is what makes the rung load-bearing. Forced to operate without a stable color-to-class convention, the model cannot memorize "red means car." Instead, it learns the abstraction that's actually useful: each sample carries an example pair (an input image plus a partial output painted with this sample's specific colors), and the model's job is to extend the partial output to cover the full image, *matching the colors the sample is using*. The problem is no longer "what class does this pixel belong to"; it's "which of the colors in the example pair does this pixel match."

That reformulation is what makes Vision Banana's prompt-based class-set flexibility work. When a Vision Banana user types `{"car": "red", "sidewalk": "blue", ...}` at inference, what they're doing is telling the model "for this prediction, here is the color-to-meaning mapping." The model is fluent in arbitrary color-to-meaning mappings because of SegGPT's training-time random-recoloring trick. The same checkpoint can serve different class sets at inference time without retraining the segmentation head, because the model never had a "segmentation head" with a fixed class set in the first place. It always had a more general capability: paint the output to match whatever color convention the example pair (or, in Vision Banana's case, the prompt) supplied.

The JSON prompt of §5 is SegGPT's contract, made explicit. The prompt declares this inference's color-to-meaning convention; the model paints; the decode reads the colors back out. That's the whole flow. Without SegGPT's training-time random color mapping, the prompt would be decorative. With it, the prompt is the lookup table.

### 12. DIFT (2023): correspondence emerges in diffusion features

The other 2023 rung is on the 3D side. Luming Tang and colleagues at Cornell published [DIFT (Diffusion Features)](https://arxiv.org/abs/2306.03881): a paper showing that the *intermediate* feature maps of a pretrained diffusion model (Stable Diffusion's UNet, in their experiments) carry dense correspondence information across images, with no explicit supervision for it.

The setup is the standard correspondence task. Take two images of the same object in different poses; pick a point on the first image; find the corresponding point on the second. Classical methods used hand-engineered features (SIFT, ORB) or learned ones (DINO, OpenCLIP). DIFT just runs both images through Stable Diffusion's UNet partway, extracts the intermediate features at some chosen layer, and finds nearest neighbors in feature space. No retraining; the diffusion model was trained for image generation and never told to do correspondence.

The paper's own number: "DIFT from Stable Diffusion is able to outperform DINO and OpenCLIP by 19 and 14 accuracy points respectively on the challenging SPair-71k benchmark."

That is a striking margin. DINO and OpenCLIP are, at the time of DIFT, the canonical pretrained encoders for tasks of this kind. Beating them by double-digit points using features that fall out of an unrelated training objective is the kind of result that reframes a research community's expectations about where useful representations live.

{/* TODO: Fig 10 (DIFTCorrespondence) - two photos of the same animal in different poses; matched correspondence pairs (e.g. left ear, right paw, eye) marked with the same color across the pair. An arrow back into a cartoon UNet showing the intermediate layer where features were extracted. The figure makes visible: a model trained only to denoise pictures also knows what's the same across pictures. */}

What DIFT *did* establish is conservative. It shows that a diffusion model's intermediate features carry dense per-pixel structure useful for at least one downstream task (correspondence). It does not directly show that the same features are sufficient for metric depth, surface normals, or any other dense-prediction task. Whether the structure-of-correspondence translates to the structure-of-depth-or-geometry was still an open question after DIFT.

But it's the rung where the *intuition* arrives. If a generator's substrate has features informative enough to find correspondences across images without any supervision aimed at that task, then maybe the substrate also has features informative enough for other dense per-pixel tasks if the right thin tuning layer is added on top. The "if" in that sentence is what Vision Banana puts to the empirical test in 2026. DIFT supplies the prior that makes the test worth running; it does not, by itself, validate the claim that depth and normals will fall out of the same substrate.

The throughline runs through DIFT in a hedged way. The depth column of §8 (VB 0.882 / 0.929 against the strongest specialists) is plausible, in retrospect, partly because DIFT showed that the same kind of substrate already contained dense correspondence. The normals column (15.549° vs 16.558°) is plausible for the same reason. DIFT didn't *prove* either column would land where it did; it raised the prior probability that the column would land at all.

### 13. Vision Banana (2026): the synthesis

Now we have the cumulative substrate. MAE established that reconstruction is a credible pretraining objective and that asymmetric encoder–decoder design is computationally tractable at scale. Painter established that the output of every vision task can be parameterized as an image, training the same architecture across tasks via stitched I/O. SegGPT added the per-sample random color mapping that lets the same model serve any class palette the user supplies at inference. DIFT showed that the intermediate features of a pretrained generator already carry enough dense per-pixel structure for at least one transfer task (correspondence), making the conjecture "this kind of substrate also supports depth and normals" worth testing. Each contribution is a discrete mechanism. None of them, on its own, was Vision Banana.

The fifth rung is scale. By November 2025, [Nano Banana Pro](https://blog.google/innovation-and-ai/products/nano-banana-pro/) was a production image generator deployed across the Gemini app, the Gemini API, Google AI Studio, and Vertex AI. It had been trained at the kind of scale that only an internet-sized data corpus and a hyperscaler's compute can buy. It was generating user-prompted images for paying customers. Whatever the right substrate was, it had to be at production scale; research-scale generators of three years earlier (the Stable Diffusion of DIFT) were no longer at the frontier. Nano Banana Pro is the substrate the Vision Banana paper was waiting for.

Vision Banana, in 2026, glues the contributions together. Take the Nano Banana Pro substrate. Add a "very low ratio" of vision-task instruction data on top, in the style Painter used (input/output stitched), with the per-sample random color mapping SegGPT added. Read perception out at inference time by prompting the model in the painted-output formats of §§5–7 (JSON-prompted segmentation; power-transformed false-color depth; xyz→RGB normals). The result is the spread of §8.

The paper's thesis sentence: "image generation serves as a unified and universal interface for vision tasks, similar to text generation's role in language understanding and reasoning." The paper *argues* that image-generation pretraining serves a role for vision analogous to next-token pretraining for language: a substrate trained on a generative objective at sufficient scale acquires representations that downstream tasks can read off via light task-specific tuning, the same way GPT-4 reads off summarization or translation by light task tuning of a next-token-pretrained model.

The arrows converge into a Vision Banana methods box; the methods box itself owns the per-task encodings (depth false-color, normals xyz-to-RGB), and those are VB's choices, not predecessor outputs. */}

Whether the paper's hypothesis (the analogy to LLM pretraining) is correct in the strong sense is what the next section qualifies. The cumulative recipe and the resulting numbers are real. Whether the right description of what's happening is "pretraining gave us the perception representations" or something subtler is an empirical question the paper does not fully resolve.

### 14. What the paper does not prove

A short section, but a load-bearing one. Vision Banana's central narrative claim, that image-generation pretraining is to vision what next-token pretraining is to language, is the paper's *hypothesis*, not its proven result. The distinction matters because a reader who treats the hypothesis as established conclusion will overstate what the field has learned.

What the paper publishes is performance numbers across five task families and a recipe that gets to those numbers. What the paper does not publish is a controlled experiment that isolates the contribution of pretraining itself. There is no random-initialization baseline: no run in which the same instruction-tuning recipe is applied to a non-pretrained generator and produces inferior numbers. There is no pretraining-recipe ablation: no comparison between Nano Banana Pro and an alternative-objective foundation model of similar scale. The performance evidence is consistent with "pretraining gave us the substrate," but it's also consistent with "the instruction-tuning data set is doing more work than the paper credits it for," or with "the production-scale architecture and compute are doing more work than the pretraining objective per se."

The deltas, too, are modest. The §8 numbers reward careful reading. Vision Banana edges SAM 3 by 4.7 points zero-shot Cityscapes, but the in-domain non-zero-shot ceiling SegMan-L sits 14.3 points above Vision Banana itself. Vision Banana beats Depth Anything 3 by 1.1 points on the four-dataset depth overlap; Depth Anything 3 is the strongest specialist Vision Banana publishes a direct comparison against. Vision Banana wins surface normals by 1.0°. Each delta is real, all four point in Vision Banana's favor, and none is large enough to feel like the specialist categories have been demolished.

What the paper *does* establish, on the evidence, is the existence proof. There is now one model that scores at or near the top across five disparate dense-prediction families at once, by treating each task as image painting with task-specific colormaps. That existence proof is the actually interesting claim, and it stands without needing any of the stronger pretraining-causal claims the paper hypothesizes about. The trilogy's argument doesn't depend on those stronger claims either.

The honesty matters because it shapes what the post should leave the reader believing. The paradigm flip is real: read perception out of a generator's painted output, instead of off the back of an encoder's head. The mechanism is reproducible (the recipe is in §§5–7, the lineage is in §§9–12). The competitive performance is documented. What's *not* yet documented, and what the post must not pretend is documented, is that pretraining-as-a-generator is *the* right pretraining choice in some absolute sense. That's tomorrow's experiment.

### 15. What the trilogy collectively argues

Step back from Vision Banana for a moment. What this site has been arguing across three posts is that the answer to "what is the spinal cord of a vision foundation model" keeps changing.

Post 1 ended at C-RADIOv4: a single encoder, agglomeratively distilled from three teachers (DINOv3, SigLIP2, SAM3), producing dense features that downstream heads could read off. The encoder was the spinal cord; the heads were the lookup. That was where the field stood at the start of 2026.

Post 2 took that encoder and bolted the rest of an omni-modal stack onto it. Modality-specific encoders for audio and video. A text decoder at the center of the system, the only organ in the architecture that could run a softmax over a vocabulary and produce sentences. A pile of token-budget machinery (tubelet fusion, EVS, hybrid Mamba+MoE, NVFP4 quantization) to keep the inference cost from collapsing under its own weight. The encoder was still the spinal cord; the decoder was the new center of gravity.

Post 3 inverts the topology. The generator is the spinal cord. There is no per-task head. There is, optionally, a text decoder for the user's prompt and a per-pixel decode lookup for whichever colormap the prompt names, but the actual perception lives in the painted RGB output. The decoder reads the model; the model reads the world.

{/* TODO: Fig 12 (TrilogyMeta) - three horizontal rows, top to bottom. Row 1 (Post 1): the same image enters an encoder; multiple small heads on the right; each head outputs a different downstream object (class label / dense mask / depth scalar). Row 2 (Post 2): the same image enters an encoder; encoder feeds into a text decoder at center; speech / video encoders feed in alongside; output is text tokens (and a speech head for audio out). Row 3 (Post 3): the same image enters a generator; a JSON prompt steers it; output is an RGB image; a decode lookup at the back reads the colors back into integers. */}

The pattern across the three rows is "fewer, larger, more general models doing more dense-prediction work from one model invocation, with whatever decode lookup at the back is needed to read the answer out." Post 1's heads were a kind of decode lookup. Post 2's text decoder is a kind of decode lookup. Post 3's color-distance lookup against a JSON prompt is a kind of decode lookup. The shape keeps changing; the shape of the question doesn't.

Each post in the trilogy is internally coherent. None of them invalidates the others. C-RADIOv4 is still a strong vision encoder; Nemotron 3 Nano Omni is still a state-of-the-art four-modality agent in May 2026; Vision Banana is now in the conversation about what the substrate of the next generation of vision foundation models should be. The question of which architecture wins in 2027, or which approach gets folded into the others, is the kind of question this site will keep returning to. The trilogy is not a final answer. It's a snapshot of three coherent answers that all happened to land within roughly twelve months of each other.

## Coda

We used to ask the encoder for a label and it gave us integers from a head. Now we ask the generator for a picture and we read the integers back out of the colors. The model emits a different shape; the lookup at the back of the system is what makes the picture mean a class.
